## 4. Deferred-Trigger Tests (unreachable from HTTP)

- [x] 4.1a Write a Testcontainers test that inserts a header row plus **balanced** `entry_lines` rows directly via `JdbcTemplate` (bypassing the domain layer's own balance check) and commits — verify the commit succeeds. This is the positive control for 4.1b: without it, a trigger that always raises would still pass 4.1b
- [x] 4.1b Same setup with **unbalanced** lines, committed under default (deferred) constraint checking — verify the commit fails with a Postgres error reporting SQLSTATE `LDG01`, and identify and assert on the concrete exception type Spring's transaction manager surfaces at commit (per design.md's noted uncertainty; this task is what resolves it)
- [x] 4.1c Same setup with three lines whose `amount_cents` are `9223372036854775807`, `9223372036854775807`, and `2` (each individually a valid `BIGINT` value, but their sum overflows it) — verify the commit still fails with SQLSTATE `LDG01`, not Postgres's own `22003` numeric-overflow error, confirming the trigger function's running-sum variable is `NUMERIC` and not `BIGINT`
- [x] 4.2a Insert a header row plus **unbalanced** lines, then issue `SET CONSTRAINTS ALL IMMEDIATE` *after* all the lines are already inserted (not before) but before commit — verify the failure surfaces at that `SET CONSTRAINTS` statement itself, with SQLSTATE `LDG01`, rather than being deferred to commit
- [x] 4.2b Same as 4.2a with **balanced** lines — verify `SET CONSTRAINTS ALL IMMEDIATE` succeeds and the subsequent commit succeeds. This is the positive control for 4.2a: without it, a trigger that always raises would still pass 4.2a. (Issuing `SET CONSTRAINTS ALL IMMEDIATE` *before* any lines are inserted is not a valid test of this path — it forces every deferred constraint to check after each individual row, so the first line of any multi-line entry would fail regardless of whether the whole entry balances.)
- [x] 4.3 Confirm none of 4.1a/4.1b/4.1c/4.2a/4.2b rely on `@Transactional`-rollback-style test isolation. A deferred trigger only evaluates at a real `COMMIT` (or an explicit `SET CONSTRAINTS ... IMMEDIATE`); Spring's test-rollback mechanism never issues a real commit, so under that isolation mode the trigger never runs at all. A rollback-style *negative* test (expecting SQLSTATE `LDG01`) would fail loudly, since the expected exception is never raised — but a rollback-style *positive-control* test (expecting success) would pass vacuously regardless of whether the trigger works, which is exactly why 4.1a and 4.2b need real-commit isolation to mean anything
